### 1.3 判定

**rn 需要两个完整轮次**：

1. **第 1 轮：DragonLib 26.3 移植**（331 java，起始 1271 错）。它是 rn 的 GUI 框架，

2. **第 2 轮：rn 本体**（546 java；dragonlib 就位后重测真实错误数）。

**不要**尝试「用空壳 DragonLib 让 rn 编过」：rn 是**重度 GUI mod**（列车仪表盘、时刻表、路线图、站牌），
GUI 桩化 = mod 失去意义（和 copycats 的判定同理）。**降级路线在这里没有交付价值。**

### 2.3 剩余 477 错的**族**与改法（下一轮照单做）

#### A. recipe 子系统 —— 142 错（**要先做，最大单块**）

**根因**：26.3 的 Create **把整套 `ProcessingRecipe` 框架删了**。逐类扫过 create jar：
`ProcessingRecipe` / `ProcessingRecipeBuilder` / `ProcessingRecipeSerializer` / `IRecipeTypeInfo` /
`SequencedAssemblySubCategoryType` / `CreateRecipeCategory` **全部 0 命中**。
26.3 换成了 **codec 化的原版配方体系** + 一组新的基础接口：

```
com.zurrtum.create.foundation.recipe.CreateRecipe<T extends RecipeInput>
        （提供 placementInfo() / recipeBookCategory() / group() / showNotification() / isSpecial() 默认值）
com.zurrtum.create.foundation.recipe.CreateSingleStackRecipe        (result() + ingredient() + matches/assemble 默认)
com.zurrtum.create.foundation.recipe.CreateRollableRecipe<T>        (assemble(T, RandomSource) -> List<ItemStack>)
com.zurrtum.create.foundation.recipe.CreateSingleStackRollableRecipe(ingredient() + results(): List<ProcessingOutput>)
com.zurrtum.create.content.processing.recipe.ProcessingOutput      （还在）
```

26.3 的原版配方 API（javap 实测）：
```java
public interface Recipe<T extends RecipeInput> {          // 注意：assemble(T) 不再带 RegistryAccess
    boolean matches(T, Level);
    ItemStack assemble(T);
    boolean showNotification();  String group();
    RecipeSerializer<? extends Recipe<T>> getSerializer();
    RecipeType<? extends Recipe<T>> getType();
    PlacementInfo placementInfo();  RecipeBookCategory recipeBookCategory();
    default List<RecipeDisplay> display();
}
public final class RecipeSerializer<T> extends Record {   // ★ 变成 record：MapCodec + StreamCodec
    RecipeSerializer(MapCodec<T>, StreamCodec<RegistryFriendlyByteBuf, T>);
}
```
⇒ 要改的文件（11 个）：`RollingRecipe`、`ChargingRecipe`、`RollingMillRecipeParams`、`ChargingRecipeParams`、
`RollingRecipeProcessingFactory`、`ChargingRecipeProcessingFactory`、
`SequencedAssemblyRollingRecipeSerializer`、`SequencedAssemblyChargingRecipeSerializer`、
`CARecipeSerializer`、`RollingMillAssemblySubCategory`/`*Rei*`/`*Emi*` 三个子分类（**直接删**，是 JEI 展示层）、
`LiquidBurningRecipe*`（**已随液体删**）。
`RollingMillBlockEntity` 里还有 18 错与它耦合：`SequencedAssemblyRecipe.getRecipe(...)`、`recipe.rollResults()`、
`assemble(inv, registryAccess)`、`ProcessingInventory`、`StorageUtil.insertStacking`。

**建议实现形态**（最省事、已验证接口存在）：
- `RollingRecipe implements CreateRecipe<RecipeWrapper>`（自己的 `RecipeWrapper`，已经是 `RecipeInput` 了）
  + 自带 `MapCodec`（`RecordCodecBuilder`：`ingredient` / `result` / `processing_time`）+ `StreamCodec.composite`
- `ChargingRecipe` 同理，字段沿用 `ChargingRecipeParams`（`energy` / `maxChargeRate` / `processingDuration`）

## 4. 踩到的坑（写进台账）

1. **CFR 的 `Unable to fully structure code`**：`rn/.../StaticTextDisplaySettings.onChangeSettings` 被反编译成
   `if (...) ** GOTO lbl-1000` + `} else lbl-1000:` ⇒ 语法错。**只能手写重推**（本轮已做，见该文件的
   `copied` 标志写法）。这类残骸在 rn 里只此一处（dragonlib 里另有两处 ObjParser 也是同类，已用
   `_fix_innernew` 修掉）。
2. **`_rewrite26.py` 之后仍然可能有 `E046` 级联**：一旦某文件语法错，javac 会**只报那个文件的错**
   （本轮 s2 后只报 30 错，全是 4 个文件的语法残骸）—— **看到错误数突然暴跌先怀疑语法，不要高兴**。
3. **Create 26.3 里 `ProcessingRecipe` 家族整体不存在**（不是换包，是**删除**）。任何 1.20.1/1.21.1 的
   Create 附属只要 extends 它，就必须改写成 codec 化的 `CreateRecipe<T>` / `CreateSingleStackRollableRecipe`。
4. **26.3 的 `RecipeSerializer` 是 record**（`MapCodec` + `StreamCodec`），`fromJson/toNetwork` 全部消失
   （报错形如 `method method_52177(JsonElement)` / `method method_8088(FriendlyByteBuf)`）。
